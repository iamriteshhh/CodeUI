Problem Statement & Motivation

The Academic Computer Laboratory Dilemma

Why commercial IDEs and bare text editors both fail during practical programming examinations
Option A: Commercial IDEs
VS Code, JetBrains CLion, Eclipse
  • Compromises Exam Integrity: IntelliSense, word completion, and snippet expansions solve syntax and logic on behalf of the student.
  • Unchecked AI Plugins: GitHub Copilot and ChatGPT plugins synthesize full solutions in seconds.
  • Heavy Memory Footprint: Consumes 300MB-800MB RAM idle, causing system lockups on older 4GB lab PCs.
Option B: Bare Editors
Notepad, gedit, nano
  • Prevents Cheating: Zero automated code suggestions or AI plugins.
  • Cripples Ergonomics: No integrated terminal—forces constant Alt-Tabbing back and forth to an external command prompt.
  • Zero Diagnostics: No visual error markers; students get lost debugging cryptic raw compiler messages.
  • No Project Views: Lacks multi-tab editing and visual directory tree management.
The Solution: CodeUI
The Best of Both Worlds
  • Guaranteed Zero Assistance: Irreversible, architectural lockdown of all autocomplete, hints, and AI extensions.
  • Modern Developer Ergonomics: Multi-tab Monaco Editor, split views, and light/dark theme support.
  • Real Integrated PTY: Built-in terminal supporting interactive scanf, cin, and Python input().
  • Visual Diagnostic Markers: Real-time compiler error squigglies with plain-English crash hints.
Workstation Security & Stability

Operational Vulnerabilities on Shared Lab Workstations

Why unmanaged execution of student code degrades physical laboratory computers
1. Orphaned Background Processes (Zombies & Loops)
When student code enters an infinite loop or spawns background processes, closing an external terminal window often leaves the process running in the background. Over multiple student batches throughout the day, CPU cores become saturated and workstation fans run at 100%.
✔ CodeUI Defense: Detached OS process groups (setsid / Win32 process flags) + 30-second watchdog timers.
2. Terminal Buffer Flooding (UI Freeze)
A novice student writing while(1) printf("%d\n", i++); outputs millions of lines per second. In standard web-based or pipe-based terminals, this floods the event queue, freezes the UI thread, and crashes the webview with Out-Of-Memory (OOM) errors.
✔ CodeUI Defense: Dual-cadence buffer throttling (30ms intervals or 8KB chunks) + 5MB hard memory cap.
3. Workspace Clutter & Polluted Submissions
Compilers (gcc, javac, sf) generate binary executables, object files, and bytecode (.exe, .class, .o) directly into the student's assignment folder. When submitting assignments via USB or portal, students zip clutter or submit the wrong files.
✔ CodeUI Defense: Automatic transient scratch directory sandboxing (clean student folders).

Execution Pipeline

End-to-End System Execution Flow

What happens step-by-step when a student clicks 'Run' in the user interface?
Step 1: UI Trigger & Save
React workspace store validates active file and automatically flushes dirty in-memory buffers to disk via fsService.
Step 2: Tauri IPC Dispatch
Dispatches commands::process::run_file(path) across Tauri's asynchronous IPC boundary with zero UI freeze.
Step 3: Runner Resolution
Rust backend maps extension (.c, .java, .py) to the appropriate LanguageRunner and allocates a transient scratch dir.
Step 4: Build & Diagnostics
Executes compiler. If build fails, captures stderr stream, parses error coordinates, and emits inline Monaco squiggly lines.
Step 5: Process Detachment
Spawns child process inside a new OS process group (libc::setsid() on Linux or Win32 creation flags).
Step 6: Throttling & Watchdog
Dual-cadence output pump buffers stdout (30ms/8KB, 5MB cap). Background watchdog monitors 30s execution ceiling.

Native Systems Core

OS-Level Process Group Detachment

Guaranteeing total termination of student programs and child subprocesses
The Danger: Process Tree Escapes
Why standard process spawning fails on lab machines:
  • Subprocess Forking: When student code executes fork() or spawns a shell subprocess, child processes are decoupled from the immediate parent.
  • Orphaned Survival: When the IDE terminates the main PID, grandchildren are adopted by init (PID 1) on Linux or continue as background tasks on Windows.
  • Workstation Freezes: Unchecked orphaned processes accumulate across multiple student batches, eventually exhausting system RAM and locking the CPU.
CodeUI Solution: Detached Groups
How CodeUI isolates process trees in Rust:
  • Linux / POSIX (libc::setsid): Calls setsid() in pre-exec hook. The child becomes a brand-new session leader and process group leader. Signals sent to -PGID kill the entire tree atomically.
  • Windows (CREATE_NEW_PROCESS_GROUP): Injects CREATE_NEW_PROCESS_GROUP | CREATE_NO_WINDOW flags into process creation attributes.
  • Deterministic Tree Kill: Dispatches taskkill /PID <pid> /T /F (/T = entire process tree, /F = force kill).
  • Zero Orphans: Guarantees 100% clean termination of every child process.
Fault Tolerance

Watchdog Timers & Escalating Termination

Automatic detection and two-stage termination of runaway student programs
1. The 30s Watchdog Budget
Autonomous Loop Detection
• Dedicated background thread monitors execution wall-clock time.
• Hard 30-second execution ceiling prevents hung processes.
• Triggers automatically if student writes while(1) {}.
• Emits human-readable notification: "Execution timed out (30s limit)".
• Keeps physical lab computers responsive.
2. Two-Stage Kill (kill_tree)
Polite Flush -> Forceful Kill
• Stage 1 (Polite): Dispatches SIGTERM to the process group.
• 500ms Grace Period: Allows pending standard I/O buffers to flush cleanly to screen.
• Stage 2 (Forceful): If process remains active after 500ms, escalates to unconditional SIGKILL.
• Ensures complete termination without corrupted buffers.
3. Window Close Enforcement
Zero Leftover Zombies
• Hooked to Tauri's CloseRequested event.
• Immediately invokes shutdown_all() across RunRegistry and PtyManager.
• When student closes app or logs off, all processes terminate immediately.
• Clean workstation state guaranteed for the next class batch.
Stability Guardrails

Dual-Cadence Output Throttling & Memory Cap

Preventing webview thread starvation and memory exhaustion from infinite print loops
The Denial-of-Service Risk
Why naive terminal output freezes IDE webviews:
  • The Infinite Print Loop: A student writes while(1) printf("%d\n", i++);. The process emits tens of thousands of lines per second.
  • Event Queue Saturation: If every print triggers an immediate IPC message, the React/webview main thread is flooded with tens of thousands of state updates.
  • Browser Out-Of-Memory: Webview memory spikes into gigabytes trying to store endless string spans, resulting in a complete browser crash.
CodeUI Defense: Dual-Cadence Pump
How CodeUI throttles output in native Rust:
  • Cadence 1 — Time Interval (30ms): Pushes buffered characters to the frontend at most once every 30 milliseconds (~33 FPS).
  • Cadence 2 — Size Chunk (8,192 Bytes): If the buffer hits 8KB before 30ms expires, it flushes immediately for high throughput.
  • Hard Memory Ceiling (5 Megabytes): Caps total output at 5MB per run. If exceeded, halts output and warns: "Output limit exceeded (5MB). Program stopped."
  • Fluid 60 FPS: UI remains 100% responsive under any print load.
Workspace Cleanliness

Transient Scratch Directory Sandboxing

Keeping student assignment workspaces clean and preventing submission errors
Traditional IDE Build Clutter
Pollution of student assignment folders:
  • Intermediate Binaries: Compilers dump .exe, .o, .class, and .pdb debug files right next to source files.
  • Polluted Submissions: Novice students accidentally zip 50MB of compiled binaries when submitting assignments to college portals or flash drives.
  • Grading Headaches: Lab evaluators have to manually hunt down and delete old binaries before recompiling student code.
CodeUI Scratch Sandboxing
How CodeUI isolates builds transparently:
  • Isolated Temp Folder: Every run allocates a private scratch directory in the OS temp folder (e.g. /tmp/codeui-run-xyz or %TEMP%\codeui-run-xyz).
  • Preserved Working Directory (CWD): Crucial design decision: The process's current working directory remains pointed at the student's folder!
  • Relative File I/O Works: Student calls like fopen("input.txt", "r") or open("data.csv") resolve correctly relative to their source code.
  • Pristine Folders: The project folder contains only clean source files.
Terminal Engineering

True Interactive PTY Terminal Emulation

Overcoming pipe redirection flaws to support interactive C, Java, and Python input
Redirected Pipe Flaw
Why naive terminals fail
• Standard pipes use block buffering (4,096 bytes).
• Prompts like printf("Enter N: "); lack a newline (\n).
• Output stays trapped in the OS buffer while scanf() blocks.
• Student sees a blank screen, thinks the IDE froze, and gets marked down.
Real PTY Master/Slave
portable-pty + xterm.js
• Allocates real pseudo-terminals (Linux /dev/pts, Windows ConPTY).
• Manages line discipline, canonical input mode, and local echo.
• Prompts appear immediately on screen before input functions block.
• Full ANSI / VT100 escape sequence support.
Python Unbuffered (-u)
Eliminating input() delays
• Python defaults to block-buffered I/O when redirected.
• PythonRunner automatically passes -u flag.
• Guarantees prompts from input("Enter name: ") display instantly.
• Window resizing via TIOCSWINSZ ioctl supports nano and curses.
Developer Ergonomics

Intelligent Compiler Diagnostic Highlighting

Real-time regex parsing of compiler stderr into inline Monaco squiggly error markers
Real-Time Stderr Parsing
How parseCompilerDiagnostics.ts works:
  • C/C++ (GCC & Clang): Extracts regex file:line:col: (error|warning): message and translates coordinates into Monaco markers.
  • Java (Javac): Matches file:line: error: message and scans subsequent lines for caret (^) column indicators.
  • Python Tracebacks: Analyzes multi-line traceback frames, extracting line numbers and exception types (IndexError, NameError).
  • Inline Squigglies: High-contrast red markers painted directly under offending source lines.
Plain-English Crash Hints
Translating cryptic exit codes for students:
  • Exit Code 139 (SIGSEGV): "Program crashed — likely a segmentation fault. You may have accessed an uninitialized pointer or an out-of-bounds array index."
  • Exit Code 136 (SIGFPE): "Arithmetic exception — likely a division by zero or modulo by zero operation in your code."
  • Exit Code 137 (SIGKILL): "Program stopped — execution took longer than the 30-second watchdog limit or was killed."
  • Exit Code 1: "Process exited with non-zero exit code 1. Check your logic and compiler warnings."
Language Runners

Advanced Java Class & Package Resolution

Pre-compilation AST validation eliminating academic ClassNotFoundException errors
The Academic Java Struggle
Common beginner mistakes in Java labs:
  • Filename Mismatch: A student writes public class BinarySearchTree inside a file named Lab3.java. javac throws a compilation error.
  • Package Pathing Failures: A student writes package com.college.ds; but executes java BinarySearchTree from inside the package directory, triggering ClassNotFoundException.
  • Lost Exam Time: Students spend 15 minutes renaming files and moving directories around instead of writing algorithms.
CodeUI JavaRunner Intelligence
How CodeUI handles Java automatically:
  • AST Pre-Flight Scanner: Parses Java source text (skipping comments and strings) to find the declared class and check if it is public.
  • Pre-Compilation Alert: If public class Calculator is in Main.java, CodeUI flags it immediately with actionable advice before javac runs.
  • Package Detection: Detects package com.college.ds; and compiles with javac -d <scratch>.
  • Automatic FQCN Execution: Automatically launches java -cp <scratch> com.college.ds.Calculator.

Engineering Decisions

Technology Stack & Technical Justification

Why Tauri 2.x and Rust were chosen over Electron and Python for CodeUI
Why Tauri + Rust Instead of Electron?
Key architectural comparisons:
  • Resource Footprint: Electron bundles full Chromium + Node.js (~150MB installer, ~300MB-800MB RAM). Tauri uses host native webview (Edge WebView2 / WebKitGTK) with ~15MB installer and ~60MB RAM.
  • Security Boundary: Electron apps frequently expose Node.js fs/child_process to renderer. Tauri enforces strongly-typed, auditable Rust commands with zero arbitrary shell access.
  • Low-Level OS Control: Rust provides zero-cost access to POSIX syscalls (setsid, killpg, ioctl TIOCSWINSZ) and Win32 process creation flags impossible in pure web tech.
The 'No-Python-Tooling' Architecture
Strict separation of build tooling from student targets:
  • Python is a Target, Not a Tool: Python is supported exclusively as an execution runtime for student assignments; it is never used in the building or testing of CodeUI itself.
  • Rust xtask Automation: All repository automation, version synchronization, and packaging tasks are built in a native Rust crate in xtask/.
  • Zero Environment Fragmentation: Developers and CI runners never need a secondary Python virtual environment (venv) or pip packages to build CodeUI.
  • Hermetic Reproducibility: Eliminates "works on my machine" dependency failures across lab machines.
